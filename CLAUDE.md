# CLAUDE.md

Инструкции для Claude Code в этом репозитории. Учебный проект: АСУ СОИТ «ТехноСервис» — система управления сервисным центром по ремонту IT-техники. Приоритет разработки: понятный код > корректная архитектура > безопасность > производительность > скорость разработки. Не использовать сложные решения без объективной необходимости — это чаще ошибка, чем достоинство.

## Границы автономности

Можно без подтверждения: анализировать код, искать баги, писать boilerplate/CRUD/SQL/тесты, рефакторить в рамках существующей архитектуры, обновлять документацию, объяснять код.

Требует остановки и вопроса пользователю **до** реализации:
- смена архитектуры или паттернов
- выбор новой библиотеки/зависимости
- изменение модели данных или схемы БД
- решения по безопасности и авторизации
- деплой и инфраструктура

Не коммитить без явного запроса. Не отключать проверки безопасности ради упрощения кода — никогда.

## Структура проекта

```
backend/
  cmd/server/       — main.go, единственная точка сборки DI
  internal/
    auth/            — JWT, middleware
    config/          — загрузка env
    db/              — пул соединений
    domain/          — Entity + DTO
    handler/         — HTTP-слой
    repository/      — SQL-слой
    router/          — регистрация маршрутов
frontend/            — пока не создана
db/migrations/       — последовательные .sql файлы
docs/                — Obsidian vault (предметная область, роли пользователей)
planning/            — STATE.md, ARCHITECTURE.md, DECISIONS.md, ROADMAP.md, CURRENT_TASK.md
```

Не менять структуру каталогов без необходимости.

## Архитектура: строго слоистая, без исключений

```
HTTP → Router → Handler → Repository → PostgreSQL
```

| Слой | Отвечает за | Запрещено |
|---|---|---|
| Router | только регистрация маршрутов | SQL, бизнес-логика, работа с БД |
| Handler | HTTP, gin.Context, binding, вызов repository, ответ через `respondOK`/`respondCreated`/`respondError` | SQL, прямой `c.JSON(...)` вместо хелперов |
| Repository | только работа с PostgreSQL, зависимость через `NewRepository(pool)` | gin, HTTP, JSON |
| Domain | Entity и DTO — не смешивать в одной структуре | — |

Вся сборка зависимостей — только в `cmd/server/main.go`, в порядке: Config → Database → Repositories → Handlers → Router → Server.

## Правила Go

Обязательно: `context.Context` первым параметром, `fmt.Errorf("%w", err)` для оборачивания ошибок, параметризованный SQL (`$1`, `$2`, …, никогда конкатенация), snake_case в JSON-тегах, `json:"-"` на секретах (пароли, хеши), nullable-поля через указатели, UUID для PK, DI через конструкторы.

Запрещено: глобальные переменные, `panic`, `init()` кроме действительно необходимых случаев.

## SQL и PostgreSQL

- Только параметризованные запросы, никогда конкатенация строк.
- Многошаговые операции — в транзакции (`Begin` / `defer tx.Rollback(ctx)` / `Commit`).
- UUID вместо `serial`, snake_case, явные FK и индексы, `timestamptz` для времени.
- PostgreSQL `enum` — только по отдельному согласованию с пользователем.

## Миграции

Все изменения схемы — только через новый файл в `db/migrations/`, по возрастающей нумерации. Существующие миграции не редактировать — даже если ошибка в них.

## Кодстайл

Предпочитать маленькие функции, читаемые имена, отсутствие дублирования, явные зависимости.
Избегать огромных файлов, магических чисел, скрытых зависимостей.

## Перед началом задачи

1. Изучить существующий код и найти аналогичную реализацию — использовать её как шаблон, не изобретать новый паттерн.
2. Следовать текущему стилю проекта.
3. Не переписывать рабочий код без причины.
4. При сомнениях в архитектурном решении — сначала спросить пользователя, не гадать.

## После изменений

Перечислить изменённые файлы, объяснить зачем, указать риски. Если изменена логика — предложить тесты; если тесты есть — прогнать их перед завершением.

## Документация проекта

Актуальное состояние вести в `planning/`:
- `STATE.md` — что реализовано / в разработке / известные проблемы (обновлять по факту кода, не дублировать эту информацию сюда, в CLAUDE.md)
- `ARCHITECTURE.md`, `DECISIONS.md`, `ROADMAP.md`, `CURRENT_TASK.md` — по смыслу названий

При создании нового модуля — обновить README (если нужно) и `docs/` (если изменена архитектура домена).

## Безопасность — держать в голове при любой правке

SQL Injection, IDOR, Broken Access Control, корректность JWT-проверок, хеширование паролей (bcrypt, никогда plain text), валидация входных данных.

Главное правило проекта: **код должен оставаться понятным человеку, который его изучает.**
