# DB_SECURITY.md

Каталог мер безопасности на уровне базы данных для АСУ СОИТ «ТехноСервис».
Документ ведётся под курсовую по предмету «Безопасность систем баз данных» и
служит одновременно источником для защиты. Формат каждой меры:

- **Угроза** — что закрываем (языком ИБ: конфиденциальность / целостность /
  доступность / least privilege / аудит / defense-in-depth);
- **Механизм** — какая возможность PostgreSQL используется;
- **Миграция** — где реализовано (`db/migrations/NNN_*.sql`, старые не редактируем);
- **Демонстрация** — команды psql, показывающие эффект;
- **Простыми словами** — заготовка объяснения для защиты.

Модель демонстрации: реальные роли БД (`CREATE ROLE`) + `SET ROLE` в psql —
это классический, узнаваемый для безопасника способ показать разграничение.
Go-приложение продолжает ходить владельцем таблиц (`asu_soit_user`) и не
затрагивается; роли — дополнительный слой для демонстрации least privilege и
(в следующих модулях) RLS.

## Анализ нормализации схемы

Проверка по нормальным формам (на 2026-07-08). **Вывод: схема в 3NF/BCNF/4NF,
структурный редизайн не требуется.**

| НФ | Статус | Комментарий |
|---|---|---|
| 1NF | ✅ | Атрибуты атомарны. `audit_log.old_data/new_data` (jsonb) — оправданное исключение: у произвольных изменений нет фиксированной схемы. |
| 2NF | ✅ | Все PK — одиночные суррогатные `uuid`; частичных зависимостей нет. Связи M:N вынесены в `request_parts`, `stock_movements`, `request_status_history`. |
| 3NF | ✅ | Было одно исключение — `repair_requests.client_id` (транзитивно через `device → client`); **устранено** в миграции 011 (колонка удалена). |
| BCNF | ✅ | Все детерминанты — потенциальные ключи (`roles.code`, `request_statuses.code`, `organizations.inn`). |
| 4NF | ✅ | Многозначных зависимостей нет — decompose не требуется. |

**Осознанные денормализации (не нарушения, выбор с обоснованием):**
- `invoices.total_amount` — снимок суммы; корректно, счёт — неизменяемый документ.
- `spare_parts.quantity_in_stock` — агрегат от `stock_movements`; держим ради
  скорости, консистентность — кандидат на триггер (см. модуль аудита/триггеров).
- `request_parts.unit_price`, `stock_movements.unit_price` — исторические цены,
  не выводятся из текущей `sale_price`. Корректно.

**Целостность на уровне логики (не нормализация):** нет БД-гарантии, что
`clients.client_type` соответствует наличию строки в `individuals`/`organizations`.
Планируется закрыть триггером, а не редизайном.

**Решение по `client_id` (принято):** колонку `repair_requests.client_id`
**удалили** (миграция 011) — строго по 3NF. Клиент заявки определяется через
её устройство (`device → client`). Бонус для защиты: это устранило и класс
рассогласованности — раньше `client_id` и `device_id` приходили в запрос
раздельно, и можно было создать заявку, где клиент не совпадает с владельцем
устройства. Теперь такое невозможно. В API создания заявки поле `client_id`
больше не принимается; в ответах клиент при необходимости выводится JOIN-ом.

## Модуль 1 — Роли БД и минимальные привилегии (least privilege)

**Миграция:** `db/migrations/010_security_roles_grants.sql`

**Угроза.** Единый привилегированный аккаунт для всего приложения — нарушение
принципа минимальных привилегий: компрометация одного узла даёт доступ ко
*всем* данным (персональные данные клиентов, хеши паролей, финансы). Нарушается
конфиденциальность и принцип разделения обязанностей.

**Механизм.** Роли PostgreSQL (`CREATE ROLE`) + `GRANT` пообъектно и
поколоночно. По умолчанию новая роль не имеет доступа ни к чему — доступ
выдаётся явно и по минимуму. Роли — глобальны для кластера, поэтому создаются
идемпотентно (`IF NOT EXISTS`).

**Матрица привилегий (кратко):**

| Роль | Может | Не может (ключевое) |
|---|---|---|
| `role_admin` | всё | — |
| `role_manager` | клиенты/устройства/заявки (SELECT+INSERT+UPDATE заявок) | склад (write), employees, audit_log |
| `role_engineer` | заявки (UPDATE), детали, склад (списание) | **invoices**, **employees** |
| `role_storekeeper` | склад (spare_parts/stock_movements) | **clients/individuals (PII)**, **invoices** |
| `role_accountant` | invoices (write), чтение заявок/клиентов | склад (write), employees |

Только `role_admin` имеет доступ к `employees` (там `password_hash`) и `audit_log`.

**Демонстрация (psql):**

```sql
SET ROLE role_storekeeper;
SELECT count(*) FROM spare_parts;   -- OK
SELECT count(*) FROM individuals;   -- ERROR: permission denied for table individuals
SELECT count(*) FROM invoices;      -- ERROR: permission denied for table invoices
RESET ROLE;

SET ROLE role_engineer;
SELECT count(*) FROM employees;     -- ERROR: permission denied for table employees
RESET ROLE;

SET ROLE role_accountant;
INSERT INTO stock_movements(...) VALUES (...);  -- ERROR: permission denied for table stock_movements
RESET ROLE;
```

Проверено — отказы приходят именно там, где ожидаются.

**Простыми словами (для защиты).** Мы не даём каждому сотруднику «ключ от всей
базы». Кладовщик работает только со складом и физически не может открыть
персональные данные клиента или финансы — на попытку база отвечает «permission
denied». Инженер не видит счетов, бухгалтер не трогает склад, а таблицу с
хешами паролей видит только администратор. Это принцип минимальных привилегий:
у роли есть ровно то, что нужно для работы, и ничего сверх того. Даже если
злоумышленник получит доступ под одной ролью, ущерб ограничен её правами.

**Связь с приложением.** Те же правила уже действуют в Go-слое (RBAC,
`RequireRole`). Дублирование намеренно — это defense-in-depth: два независимых
рубежа (приложение и СУБД). Обход приложения (прямой доступ к БД) упрётся в
права ролей.

## Модуль 2 — Row-Level Security (RLS)

**Миграция:** `db/migrations/012_security_rls_requests.sql`

**Угроза.** GRANT (модуль 1) даёт доступ к таблице целиком. Но инженер не
должен видеть и менять чужие заявки — только свои. Без RLS любой, у кого есть
SELECT на `repair_requests`, видит все строки. Нарушение конфиденциальности и
принципа «доступ только к своим данным».

**Механизм.** `ENABLE ROW LEVEL SECURITY` + политики (`CREATE POLICY`).
Показаны два уровня:
- **грубый (по роли):** политика `rr_staff_all` — `role_admin/manager/accountant/storekeeper` видят все строки (`USING (true)`);
- **тонкий (по сотруднику):** политика `rr_engineer_own` — `role_engineer` видит только строки, где `assigned_to` = его id из сессии.

Личность передаётся сессионной переменной `app.current_employee_id` (в бою её
ставит приложение из JWT: `SET app.current_employee_id='<uuid>'`). При
неустановленной переменной инженер не видит ничего (**fail-closed**).

**Демонстрация (psql):**

```sql
-- инженер, представившийся сотрудником X
SET ROLE role_engineer;
SET app.current_employee_id = '<uuid сотрудника X>';
SELECT problem_description FROM repair_requests;   -- только заявки, где assigned_to = X
UPDATE repair_requests SET ... WHERE <чужая>;       -- UPDATE 0 (чужая строка не видна)
RESET ROLE;

-- инженер без личности → 0 строк (fail-closed)
SET ROLE role_engineer; SELECT count(*) FROM repair_requests;  -- 0

-- менеджер → видит все
SET ROLE role_manager; SELECT count(*) FROM repair_requests;   -- все
```

Проверено: инженер видит только свою заявку; чужую не видит и не может изменить
(`UPDATE 0`); без личности — 0 строк; менеджер видит все.

**Важно про владельца.** RLS **не действует** на владельца таблицы
(`asu_soit_user`) и суперпользователя — они обходят политики. Поэтому Go-
приложение (ходит владельцем) не затрагивается (проверено: `GET /requests`
по-прежнему отдаёт все заявки). Демонстрация идёт под невладельческими ролями
через `SET ROLE`. В продакшене приложение подключалось бы невладельческой ролью
и ставило бы `app.current_employee_id` на каждый запрос — тогда RLS
распространялся бы и на него.

**Простыми словами (для защиты).** Мало сказать «инженеру можно смотреть
заявки». Нужно, чтобы каждый инженер видел только *свои*. RLS вешает на таблицу
правило-фильтр: база сама, на уровне каждого запроса, показывает только те
строки, что разрешены текущему сотруднику. Чужая заявка для инженера как будто
не существует — он её не увидит и не изменит. Это разграничение доступа не по
таблицам, а по конкретным строкам.

## Модуль 3 — Представления и маскирование PII

**Миграция:** `db/migrations/013_security_views_masking.sql`

**Угроза.** Даже роль с легитимным доступом к таблице получает *все* её
столбцы. Бухгалтеру нужно опознать клиента для счёта — но паспорт и ИНН ему
видеть незачем; сотрудникам нужно знать, кто назначен на заявку — но не хеш
пароля. Выдача таблицы целиком нарушает минимизацию и конфиденциальность
персональных данных (152-ФЗ).

**Механизм.** Представления (`CREATE VIEW`) как контролируемая витрина:
- **сокрытие столбца** — `v_employees` не содержит `password_hash` вовсе
  (секрет структурно отсутствует, а не «спрятан»);
- **маскирование** — `v_individuals` / `v_organizations` через `CASE ...
  current_user` показывают паспорт/ИНН полностью только роли `role_admin`,
  остальным — маску (`******`, `****`).

Представление читает базовую таблицу правами своего владельца, поэтому роль
пользуется витриной, **не имея доступа к самой таблице**. Ключевой момент:
маска работает лишь тогда, когда витрина — единственный путь к данным. Поэтому
у `role_accountant` отозван прямой `SELECT` на `individuals`/`organizations`
(был выдан в модуле 1) — иначе маску можно было бы обойти, прочитав таблицу
напрямую (проверено: до отзыва бухгалтер видел паспорт в открытую).

**Демонстрация (psql):**

```sql
-- витрина сотрудников: столбца password_hash в ней просто нет
\d v_employees
SET ROLE role_engineer;
SELECT last_name, login, role_code FROM v_employees;  -- OK, без хеша
SELECT password_hash FROM employees;                   -- ERROR: permission denied
RESET ROLE;

-- маскирование паспорта
SET ROLE role_accountant;
SELECT last_name, passport_number FROM individuals;              -- ERROR: permission denied
SELECT last_name, passport_number FROM v_individuals;           -- ****** (маска)
RESET ROLE;
SET ROLE role_admin;
SELECT last_name, passport_number FROM v_individuals;           -- полный паспорт
RESET ROLE;
```

Проверено: инженер читает витрину без хеша, но к таблице `employees` доступа
нет; бухгалтер к `individuals` напрямую — `permission denied`, через витрину —
маска `******`; админ через ту же витрину — полный паспорт. Организации
маскируются идентично (ИНН/КПП → `****`).

**Простыми словами (для защиты).** Витрина — это «окно» в таблицу, через
которое видно ровно то, что положено. Сотруднику в окне видны имена коллег, но
не хеши паролей — этого столбца в окне вообще нет. Бухгалтеру видно, что клиент
— Иванов, но вместо паспорта стоят звёздочки. При этом саму таблицу с паспортами
бухгалтер открыть не может — только через окно с маской. Так мы отдаём каждому
минимум данных для работы, а персональные данные не «утекают» вместе с остальными
столбцами.

## Модуль 4 — Триггеры и аудит (`audit_log`)

**Миграция:** `db/migrations/014_security_audit_triggers.sql`

**Угроза.** Без журнала изменений невозможно расследовать инцидент: кто
изменил статус заявки, кто правил учётную запись, кто удалил счёт. Если
журналирование делает само приложение, его можно «забыть», обойти прямым
доступом к БД или отключить в коде. Нарушается неотказуемость (non-repudiation)
и целостность контроля.

**Механизм.** Триггеры (`CREATE TRIGGER` + функция `plpgsql`) переносят аудит
на уровень СУБД:
- **`fn_audit()`** — универсальная функция, навешена `AFTER INSERT/UPDATE/DELETE`
  на `repair_requests`, `invoices`, `employees`. Пишет в `audit_log`: кто
  (`app.current_employee_id` из сессии), что (`TG_TABLE_NAME`, `TG_OP`,
  `record_id`), снимки `old_data`/`new_data` (jsonb).
- **`SECURITY DEFINER`** — функция выполняется правами владельца
  (суперпользователь), поэтому запись в журнал проходит, даже если изменение
  сделала роль без прав на `audit_log` (напр. инженер правит свою заявку).
  Прямого `INSERT` в `audit_log` у ролей нет — журнал пополняется ТОЛЬКО
  триггером. `SET search_path` фиксирован (защита от подмены имён, см. модуль 5).
- **вырезание секретов** — из снимка удаляется `password_hash`
  (`to_jsonb(NEW) - 'password_hash'`), чтобы хеши паролей не утекли в журнал.
- **append-only** — триггер `fn_audit_guard()` (`BEFORE UPDATE/DELETE` на
  `audit_log`) запрещает изменять и удалять записи: историю нельзя переписать
  задним числом.

В отличие от RLS, **триггеры срабатывают и для владельца, и для
суперпользователя** — журналирование нельзя обойти, просто зайдя под
привилегированной ролью.

**Демонстрация (psql):**

```sql
-- 1. изменение заявки → запись появляется сама
SET app.current_employee_id = '<uuid сотрудника>';
UPDATE repair_requests SET problem_description = problem_description || ' [demo]' WHERE id = '<...>';
SELECT table_name, action, old_data->>'problem_description', new_data->>'problem_description'
  FROM audit_log ORDER BY created_at DESC LIMIT 1;   -- UPDATE, old/new значения

-- 2. изменение сотрудника → password_hash в журнал НЕ попадает
UPDATE employees SET is_active = is_active WHERE id = '<...>';
SELECT (new_data ? 'password_hash') AS hash_leaked FROM audit_log
  WHERE table_name='employees' ORDER BY created_at DESC LIMIT 1;   -- f

-- 3. журнал неизменяем
DELETE FROM audit_log;                 -- ERROR: append-only
UPDATE audit_log SET action='HACK';    -- ERROR: append-only
```

Проверено: правка заявки/сотрудника автоматически порождает запись с автором и
снимками до/после; `password_hash` в журнал не попадает (`hash_leaked = f`);
`DELETE`/`UPDATE` по `audit_log` отклоняются. Триггер сработал и под
суперпользователем.

**Простыми словами (для защиты).** Мы не полагаемся на то, что программа
«не забудет» записать, кто что менял. Сама база на каждое изменение важной
таблицы автоматически делает запись в журнале: кто, когда, что было и что
стало. Эту запись нельзя ни отключить из приложения, ни обойти прямым доступом
к базе — журнал ведёт сама СУБД, даже для администратора. И переписать журнал
задним числом тоже нельзя: изменение и удаление его строк запрещены. Пароли в
журнал не попадают — их хеш вырезается. Это даёт неотказуемость: по любому
инциденту видно, кто его вызвал.

**Связь с приложением (доработка).** Сейчас приложение ходит суперпользователем
и не выставляет `app.current_employee_id`, поэтому его записи ложатся с
`employee_id = NULL` (журнал всё равно ведётся). Чтобы фиксировать автора,
приложение должно на каждый запрос выполнять `SET app.current_employee_id`
из JWT — отдельная бэкенд-задача (аккуратно с пулом соединений `pgxpool`).
