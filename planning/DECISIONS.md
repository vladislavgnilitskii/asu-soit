## 2026-07-09 — Безопасность БД (курсовая), проброс личности из JWT

### D-024. Транзакция-на-запрос + Querier для app.current_employee_id
Приложение пробрасывает личность сотрудника из JWT в сессию БД (для RLS и
аудита). Выбран вариант **транзакция-на-запрос**: middleware `auth.TxPerRequest`
(после `RequireAuth`) открывает транзакцию, ставит `set_config(
'app.current_employee_id', $1, true)` (is_local — очищается сам, утечки между
запросами через пул нет; значение параметром — без инъекции), кладёт транзакцию
в контекст. Репозитории получают executor через `dbtx.From(ctx, r.db)` (новый
пакет `internal/dbtx`, интерфейс `DBTX` удовлетворяют и пул, и `pgx.Tx`): все
запросы одного HTTP-запроса идут в одной транзакции. Commit — при `status<400`,
иначе откат. Затрагивает 6 репозиториев (`r.db.` → `r.q(ctx).`), роутер (+pool),
main. Проверено рантаймом: аудит записал автора. **Ограничение:** приложение
ходит суперпользователем → RLS к нему пока не применяется (нужен перевод на
`role_*`). Альтернативы (SET LOCAL только в имеющихся tx; пиннинг соединения)
отклонены как частичные/менее чистые.

## 2026-07-09 — Безопасность БД (курсовая), Модуль 4

### D-023. Модуль 4: триггеры аудита в audit_log
Аудит перенесён на уровень СУБД (миграция 014). Универсальная `fn_audit()`
(`AFTER INSERT/UPDATE/DELETE`) навешена на `repair_requests`, `invoices`,
`employees` и пишет в `audit_log` автора (`app.current_employee_id`), действие,
`record_id`, снимки old/new (jsonb). Решения: **SECURITY DEFINER** + фиксированный
`search_path` — чтобы запись проходила даже для ролей без прав на `audit_log`
(прямого INSERT у них нет, журнал пополняется только триггером); **вырезание
`password_hash`** из снимка (не логируем секреты); **append-only** через
`fn_audit_guard()` (`BEFORE UPDATE/DELETE` на `audit_log`) — историю нельзя
переписать. Триггеры срабатывают и под владельцем/суперпользователем (в отличие
от RLS) — аудит необходуемо. Проверено в psql. **Открытый вопрос:** приложение
пока не выставляет `app.current_employee_id` → его записи с `employee_id=NULL`;
проброс личности из JWT в сессию БД — отдельная бэкенд-задача (пул `pgxpool`).

## 2026-07-09 — Безопасность БД (курсовая), Модуль 3

### D-022. Модуль 3: представления и маскирование PII
Добавлены витрины (миграция 013): `v_employees` без `password_hash`
(сокрытие столбца), `v_individuals`/`v_organizations` с маскированием
паспорта/ИНН через `CASE ... current_user = 'role_admin'` (полные данные —
только админу). У `role_accountant` **отозван** прямой `SELECT` на
`individuals`/`organizations` (выдан в модуле 1) и оставлена единственная точка
доступа — маскирующая витрина; иначе маску можно было бы обойти чтением таблицы
напрямую (проверено до отзыва). Маскирование опирается на `current_user` внутри
представления (= роль запроса), доступ к базовой таблице — правами владельца
витрины. Проверено в psql. Приложение ходит суперпользователем — правки ролей
его не затрагивают.

## 2026-07-08 — Безопасность БД (курсовая), Модуль 2

### D-021. Модуль 2: RLS на repair_requests (роль + сессионная переменная)
Включён RLS на `repair_requests` (миграция 012). Политика `rr_staff_all` —
персонал (admin/manager/accountant/storekeeper) видит все строки; `rr_engineer_own`
— инженер видит только `assigned_to = current_setting('app.current_employee_id')`.
Личность передаётся сессионной переменной (в бою — из JWT), при её отсутствии
fail-closed (0 строк). **Модель:** DB-роль (через `SET ROLE`) = уровень
доступа, сессионная переменная = личность сотрудника. Владелец/суперпользователь
обходят RLS, поэтому Go-приложение (ходит владельцем) не затрагивается —
демонстрация под невладельческими ролями в psql. Проверено рантаймом.

## 2026-07-08 — Безопасность БД (курсовая), Модуль 1

### D-020. Нормализация: одна правка до строгой 3NF (`client_id` удалён)
Формальный разбор (см. `DB_SECURITY.md`) показал: схема в 3NF/BCNF/4NF, кроме
транзитивной зависимости `repair_requests.client_id` (выводится через
`device → client`). **Решение: колонку удалили** (миграция 011) — строго по 3NF;
это также устранило класс рассогласованности (client_id мог не совпадать с
владельцем устройства). Правки в Go: убраны поля из `RepairRequest` и
`CreateRepairRequestDTO`, `client_id` вычищен из запросов `request_repo.go`.
Денормализации `invoices.total_amount`, `spare_parts.quantity_in_stock`,
`*.unit_price` — осознанные, оставлены. Структурный редизайн сверх этого не нужен.

### D-019. Демонстрация DB-security через реальные роли + `SET ROLE`
Меры безопасности БД оформляются как отдельные нумерованные миграции +
демо-скрипты psql + запись в `DB_SECURITY.md` (угроза → механизм → демо →
объяснение). Демонстрация — через реальные роли БД и `SET ROLE` (узнаваемо для
экзаменаторов-безопасников). Go-приложение продолжает ходить владельцем
(`asu_soit_user`) и не затрагивается. **Почему:** цель — наглядно защитить
работу, не переписывая рабочий бэкенд.

### D-018. Модуль 1: роли БД + least-privilege GRANT
Созданы роли `role_admin/manager/engineer/storekeeper/accountant` с
минимальными привилегиями (миграция 010). `employees` (с `password_hash`) и
`audit_log` — только `role_admin`; `role_storekeeper` не видит PII клиентов и
финансы; и т.д. Роли создаются идемпотентно (глобальны для кластера). Это
второй рубеж поверх app-level RBAC (defense-in-depth).

## 2026-07-08 — Этап 5: Управление сотрудниками

### D-017. Сотрудников не удаляют — деактивируют (`is_active=false`)
Нет эндпоинта DELETE. Отключение через `PATCH /employees/:id` с `is_active=false`.
**Почему:** на сотрудника ссылаются `repair_requests.assigned_to`,
`request_status_history.changed_by`, `stock_movements.employee_id` — физическое
удаление порвало бы историю (или заблокировалось FK). Деактивированный
сотрудник не проходит логин (проверка `is_active` в `auth.go` уже была).

### D-016. Пароль хешируется bcrypt в хендлере при создании
`bcrypt.GenerateFromPassword` вызывается в `EmployeeHandler.Create`; в
репозиторий и БД уходит только хеш, plain-пароль нигде не хранится. Хеширование
живёт в хендлере (не в репозитории) — симметрично сверке `CompareHashAndPassword`
при логине. На входе — валидация `min=6`. В ответе API хеша нет (`json:"-"`),
и `SELECT` для чтения списка/карточки его вообще не грузит.

### D-015. RBAC модуля Сотрудники — admin-only, на всю группу
Все операции с `/employees` (включая чтение) — только роль `admin`, через
`employees.Use(RequireRole("admin"))` на группу, а не на каждый маршрут.
**Почему:** управление учётками и просмотр списка персонала — зона одного
администратора; групповое ограничение короче и не даёт забыть роль на новом
маршруте. Первое использование group-level `RequireRole`.

## 2026-07-08 — Этап 4: Финансы

### D-014. Смена статуса счёта — только pending → paid/cancelled
`UpdateStatus` использует условный UPDATE (`WHERE id = $2 AND status = 'pending'`);
если строка не обновилась — уточняющим чтением различаем «счёта нет»
(`ErrInvoiceNotFound`, 404) и «уже не pending» (`ErrInvoiceNotPending`, 409).
Хендлер отдельно валидирует, что целевой статус — `paid` или `cancelled` (400).
**Почему:** оплаченный/отменённый счёт — финальное состояние, его нельзя
переоткрывать; проверка «только pending» на уровне SQL атомарна.

### D-013. Один счёт на заявку, только по закрытой; без транзакции
Счёт выставляется только если `repair_requests.closed_at IS NOT NULL`
(иначе `ErrRequestNotClosed`, 409). Повторный счёт по заявке ловится через
`UNIQUE(request_id)` → код Postgres `23505` → `ErrInvoiceExists` (409).
Транзакция **не используется**: операция делает несколько чтений и ровно
одну запись, а от дубля защищает констрейнт БД — тот же принцип, что и в
D-009 (не усложнять там, где гонка не создаёт неверного состояния).

### D-012. Сумма счёта считается на сервере, не принимается от клиента
`total_amount = COALESCE(final_cost, 0) + COALESCE(SUM(request_parts), 0)`.
DTO создания счёта отсутствует вовсе — эндпоинт берёт только `request_id` из
URL. **Почему:** сумма — производная от уже зафиксированных данных (работа +
выданные детали по цене на момент выдачи); принимать её от клиента = дать
занизить счёт (та же логика, что D-010 с ценой детали). `COALESCE` нужен, т.к.
`SUM` по пустому набору и nullable `final_cost` дают NULL.

### D-007-finance. RBAC модуля Финансы — первое использование роли `accountant`
`POST /requests/:id/invoice` (выставить) и `PATCH /invoices/:id/status`
(оплата/отмена) — `admin, accountant`. Чтение (`GET /invoices/:id`,
`GET /requests/:id/invoice`) — любой авторизованный. **Почему:** финансовые
операции — зона бухгалтерии; это первый модуль, где нужна роль `accountant`
(по аналогии с `storekeeper` в Этапе 3). Способ оплаты (`payment_method`,
enum в БД) намеренно отложен — под него нет колонки, добавление = миграция.

## 2026-07-02 — Этап 3: Склад

### D-011. Блокировка строки (`FOR UPDATE`) при списании и выдаче
`WriteOff` и `IssueToRequest` читают остаток детали через
`SELECT ... FOR UPDATE` внутри транзакции, а не простым `SELECT`.
**Почему:** без блокировки два параллельных запроса могут оба прочитать один
и тот же остаток, оба посчитать, что деталей хватает, и оба списать — итог
уйдёт в минус в обход проверки на уровне приложения (проверка на уровне БД,
`CHECK quantity_in_stock >= 0`, в этот момент лишь оборвёт один из двух
запросов с грязной ошибкой, а не предотвратит саму гонку). `FOR UPDATE`
сериализует конкурентные транзакции на этой строке.

### D-010. Цена выдачи в ремонт берётся из `sale_price`, не от клиента
`IssuePartToRequestDTO` не содержит `unit_price` — сервер сам подставляет
`spare_parts.sale_price` на момент выдачи. Для списания (`WriteOff`) в
`stock_movements` пишется `purchase_price` (внутренняя потеря, не выставляется
клиенту). **Почему:** если бы цену передавал вызывающий, кто угодно с ролью
engineer/storekeeper мог бы выставить клиенту 1 рубль за деталь — цена
занижения/завышения счёта должна быть источником истины сервера, не ввода.

### D-009. Обработка `uq_request_parts` через код ошибки Postgres, а не пред-проверку
Повторная выдача той же детали на ту же заявку ловится через
`pgconn.PgError.Code == "23505"` (unique_violation) → `ErrAlreadyIssued`,
а не через `SELECT EXISTS` перед `INSERT`, как в остальных проверках проекта
(§5.7, `ErrCategoryNotFound`). **Почему:** между «проверили — вставили» есть
окно гонки (два параллельных запроса на выдачу одной детали на одну заявку
оба пройдут пред-проверку и оба попытаются вставить). Констрейнт в БД —
источник истины и не может быть обойдён гонкой; предварительная проверка
годится только там, где гонка не создаёт неверного состояния (например,
`status_id`/`category_id` — справочники, которые не создаются параллельно
с записью, ссылающейся на них).

### D-007-warehouse. RBAC модуля Склад — первое использование роли `storekeeper`
`POST /spare-parts`, `POST /spare-parts/:id/receive`, `POST /spare-parts/:id/writeoff`
— `admin, storekeeper`. `POST /requests/:id/parts` (выдача в ремонт) —
`admin, storekeeper, engineer` (кладовщик физически выдаёт со склада, инженер
может списать то, что сам поставил в ремонт). Чтение (`GET /spare-parts*`,
`GET /part-categories`, `GET /requests/:id/parts`) — любой авторизованный.
**Почему:** это первый модуль, где реально нужна роль `storekeeper`, заведённая
в БД с самого начала, но не используемая до этого момента (см. D-001).

## 2026-07-02 — Этап 2: Заявки end-to-end

### D-008. Валидация до изменения статуса (закрывает STATE §5.7)
Перед сменой статуса репозиторий проверяет существование `status_id`
(`ErrStatusNotFound` → 400) и заявки (`RowsAffected==0` → `ErrRequestNotFound`
→ 404). Введены sentinel-ошибки `repository.ErrRequestNotFound`/`ErrStatusNotFound`,
которые хендлеры мапят через `errors.Is`. **Почему:** раньше несуществующий id
давал 500 по FK-нарушению; теперь клиент получает корректный 400/404.

### D-007. Жизненный цикл заявки и его RBAC
Добавлены эндпоинты:

| Эндпоинт | Назначение | Роли |
|---|---|---|
| `PATCH /requests/:id/assign` | назначить исполнителя | admin, manager |
| `PATCH /requests/:id` | диагностика/стоимость (частично) | admin, manager, engineer |
| `PATCH /requests/:id/close` | закрыть (status=closed, closed_at, история) | admin, manager |
| `GET /requests/:id/history` | история статусов | любой авторизованный |

**Решения:** диагностику/стоимость ведёт инженер (+ приёмка); назначение и
закрытие — приёмка/менеджмент. `assigned_to` — любой существующий сотрудник
(целостность гарантирует FK; ограничение «только engineer» не вводим, чтобы не
усложнять). Частичное обновление диагностики/стоимости — через указатели в DTO +
`COALESCE` (nil = не менять; сброс в NULL намеренно не поддержан). Закрытие пишет
запись в историю от автора из JWT.

## 2026-07-02 — Этап 1: Клиенты-организации и устройства

### D-006. RBAC модуля Devices
`POST /devices` — роли `admin, manager` (устройство регистрируется при приёмке,
как и клиент/заявка). `GET /devices`, `GET /devices/:id`, `GET /device-types` —
любой авторизованный. **Почему:** согласуется с матрицей приёмки из D-001.

### D-005. Организации реализованы; GET /clients/:id отдаёт подтип
`CreateClientRequest` расширен полями организации (`name/inn/kpp/contact_person`);
для организации обязательны `name` и `inn` (проверка в хендлере, т.к. в одном DTO

возвращает `ClientDetails` — клиента вместе с вложенным `individual`/`organization`.
**Почему:** без этого данные организации нельзя было ни создать, ни прочитать.

## 2026-07-02 — Этап 0: Стабилизация

### D-004. Fail-fast на небезопасные секреты в production
`config.Load` завершает процесс (`log.Fatal`), если `APP_ENV=production`, а
`JWT_SECRET`/`DB_PASSWORD` пустые или равны дефолтным значениям для разработки.
**Почему:** нельзя случайно поднять прод с общеизвестными dev-секретами. В
development дефолты сохраняются — удобно для локального запуска.

### D-003. Клиенты-организации временно отклоняются (HTTP 501)
`POST /clients` с `client_type=organization` возвращает 501. Раньше код молча
создавал строку в `clients` без строки в `organizations` (orphan, нарушение
целостности).
**Почему:** полноценная поддержка организаций требует полей `name/inn/kpp` в DTO
и записи в `organizations` — это отдельная задача (новый функционал). До неё
честный отказ безопаснее порчи данных. **Следующий шаг:** реализовать организации
в рамках этапа «Клиенты и устройства».

### D-002. Автор изменения статуса — строго из JWT
`employee_id` для `request_status_history.changed_by` берётся из claims JWT
(`c.GetString("employee_id")`), а не из заголовка `X-Employee-ID`.
**Почему:** заголовок задаёт клиент — это позволяло подделать чужого автора
(spoofing/IDOR). Источник истины — только подписанный токен.

### D-001. Матрица ролей (RBAC) для текущих эндпоинтов
Согласовано с пользователем:

| Эндпоинт | Роли |
|---|---|
| `POST /clients` | admin, manager |
| `GET /clients`, `GET /clients/:id` | любой авторизованный |
| `POST /requests` | admin, manager |
| `PATCH /requests/:id/status` | admin, manager, engineer |
| `GET /requests`, `GET /requests/:id` | любой авторизованный |

**Почему:** приёмку (клиенты, создание заявок) ведут admin/manager; смену статуса
ремонта — те, кто им занимается (+ engineer). Роли `storekeeper`/`accountant`/
`sysadmin` получат доступ при появлении своих модулей (склад/финансы/админка).

### D-000. Миграция 009 (индексы) подготовлена, но не применена
`db/migrations/009_optimize_indexes.sql` удаляет дубли-индексы и добавляет
индексы на FK. **К живой БД не применялась** — применение = изменение схемы,
требует явного подтверждения пользователя (правило CLAUDE.md).
