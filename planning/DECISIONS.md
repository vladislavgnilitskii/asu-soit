## 2026-07-02 — Этап 2: Заявки end-to-end

### D-008. Валидация до изменения статуса (закрывает STATE §5.7)
Перед сменой статуса репозиторий проверяет существование `status_id`
(`ErrStatusNotFound` → 400) и заявки (`RowsAffected==0` → `ErrRequestNotFound`
→ 404). Введены sentinel-ошибки `repository.ErrRequestNotFound`/`ErrStatusNotFound`,
которые хендлеры мапят через `errors.Is`. **Почему:** раньше несуществующий id
давал 500 по FK-нарушению; теперь клиент получает корректный 400/404.

### D-007. Жизненный цикл заявки и его RBAC
Добавлены эндпоинты:

| Эндпоинт | Назначение | Роли |
|---|---|---|
| `PATCH /requests/:id/assign` | назначить исполнителя | admin, manager |
| `PATCH /requests/:id` | диагностика/стоимость (частично) | admin, manager, engineer |
| `PATCH /requests/:id/close` | закрыть (status=closed, closed_at, история) | admin, manager |
| `GET /requests/:id/history` | история статусов | любой авторизованный |

**Решения:** диагностику/стоимость ведёт инженер (+ приёмка); назначение и
закрытие — приёмка/менеджмент. `assigned_to` — любой существующий сотрудник
(целостность гарантирует FK; ограничение «только engineer» не вводим, чтобы не
усложнять). Частичное обновление диагностики/стоимости — через указатели в DTO +
`COALESCE` (nil = не менять; сброс в NULL намеренно не поддержан). Закрытие пишет
запись в историю от автора из JWT.

## 2026-07-02 — Этап 1: Клиенты-организации и устройства

### D-006. RBAC модуля Devices
`POST /devices` — роли `admin, manager` (устройство регистрируется при приёмке,
как и клиент/заявка). `GET /devices`, `GET /devices/:id`, `GET /device-types` —
любой авторизованный. **Почему:** согласуется с матрицей приёмки из D-001.

### D-005. Организации реализованы; GET /clients/:id отдаёт подтип
`CreateClientRequest` расширен полями организации (`name/inn/kpp/contact_person`);
для организации обязательны `name` и `inn` (проверка в хендлере, т.к. в одном DTO
сосуществуют поля обоих подтипов). `POST /clients` с `organization` больше не
возвращает 501 (отменяет временное решение D-003). `GET /clients/:id` теперь
возвращает `ClientDetails` — клиента вместе с вложенным `individual`/`organization`.
**Почему:** без этого данные организации нельзя было ни создать, ни прочитать.

## 2026-07-02 — Этап 0: Стабилизация

### D-004. Fail-fast на небезопасные секреты в production
`config.Load` завершает процесс (`log.Fatal`), если `APP_ENV=production`, а
`JWT_SECRET`/`DB_PASSWORD` пустые или равны дефолтным значениям для разработки.
**Почему:** нельзя случайно поднять прод с общеизвестными dev-секретами. В
development дефолты сохраняются — удобно для локального запуска.

### D-003. Клиенты-организации временно отклоняются (HTTP 501)
`POST /clients` с `client_type=organization` возвращает 501. Раньше код молча
создавал строку в `clients` без строки в `organizations` (orphan, нарушение
целостности).
**Почему:** полноценная поддержка организаций требует полей `name/inn/kpp` в DTO
и записи в `organizations` — это отдельная задача (новый функционал). До неё
честный отказ безопаснее порчи данных. **Следующий шаг:** реализовать организации
в рамках этапа «Клиенты и устройства».

### D-002. Автор изменения статуса — строго из JWT
`employee_id` для `request_status_history.changed_by` берётся из claims JWT
(`c.GetString("employee_id")`), а не из заголовка `X-Employee-ID`.
**Почему:** заголовок задаёт клиент — это позволяло подделать чужого автора
(spoofing/IDOR). Источник истины — только подписанный токен.

### D-001. Матрица ролей (RBAC) для текущих эндпоинтов
Согласовано с пользователем:

| Эндпоинт | Роли |
|---|---|
| `POST /clients` | admin, manager |
| `GET /clients`, `GET /clients/:id` | любой авторизованный |
| `POST /requests` | admin, manager |
| `PATCH /requests/:id/status` | admin, manager, engineer |
| `GET /requests`, `GET /requests/:id` | любой авторизованный |

**Почему:** приёмку (клиенты, создание заявок) ведут admin/manager; смену статуса
ремонта — те, кто им занимается (+ engineer). Роли `storekeeper`/`accountant`/
`sysadmin` получат доступ при появлении своих модулей (склад/финансы/админка).

### D-000. Миграция 009 (индексы) подготовлена, но не применена
`db/migrations/009_optimize_indexes.sql` удаляет дубли-индексы и добавляет
индексы на FK. **К живой БД не применялась** — применение = изменение схемы,
требует явного подтверждения пользователя (правило CLAUDE.md).
